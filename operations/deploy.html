배포 ​

클라이언트(Hosting), Cloud Functions, 보안 규칙(Firestore·Storage), 인덱스·TTL은 서로 맞물려 있습니다. 예를 들어 새 클라이언트는 Circle 참여에 joinCircle 함수를 쓰고, 새 규칙은 그에 맞춰 클라이언트의 멤버십 쓰기를 막습니다. 그래서 항상 같은 커밋 기준으로 함께 배포합니다.

프로덕션 배포는 항상 저장소 소유자의 확인을 받은 뒤 진행합니다.

준비물 ​

항목확인 방법
Firebase CLI가 프로젝트 소유자 계정으로 로그인firebase login, firebase projects:list에 프로젝트가 보이는지
기본 프로젝트.firebaserc의 default (firebase use)
Blaze 요금제Cloud Functions 사용에 필요
Google Cloud ADC (스크립트용)gcloud auth application-default login — backfillPublicNames, seedQuestions, purgeAiData 스크립트가 사용
약관 값src/content/legal.js에 채우지 않은 자리 표시(중괄호 두 겹 값)가 남아 있지 않은지. 남아 있으면 Hosting 배포가 거부됨(아래)
클라이언트 .env운영 프로젝트 값으로 채워져 있는지 (환경 변수). 값이 빠지면 npm run build가 실패하도록 막혀 있음 — 설정 없이 빌드하면 앱이 시작하자마자 멈추고 미리 렌더링된 글자만 보이기 때문

배포 순서 ​

서버(함수·규칙·인덱스)와 기본 질문을 먼저 준비하고 클라이언트(Hosting)를 마지막에 올립니다. 새 클라이언트는 새 callable과 규칙, 새 인덱스를 쓰는 질문 쿼리, 시드된 기본 질문을 기대하기 때문입니다. 반대로 서버를 먼저 올려도 예전 클라이언트는 그대로 동작합니다.

1. 테스트와 빌드 ​

bash
npm test && (cd functions && npm test) && (cd tests/rules && npm test)   # 권장
(cd functions && npm run test:e2e)   # 함수 엔드투엔드 (에뮬레이터, JDK 21)
npm run build                    # dist/ + prerender (.env 값이 빠지면 실패)
cd functions && npm run build    # lib/ + 공유 페이지 템플릿 복사

루트 빌드를 먼저 해야 함수 빌드가 최신 dist/index.html을 템플릿으로 복사합니다. 4번의 스크립트도 이 빌드 결과(functions/lib/)로 실행합니다.

2. 서버 배포 ​

bash
firebase deploy --only functions,firestore,storage

firestore는 규칙, 복합 인덱스, TTL 정책(fieldOverrides)을 함께 올립니다. 확인 프롬프트가 나오면 아래 표를 봅니다.

3. 인덱스와 TTL 확인 ​

새 복합 인덱스는 만드는 데 몇 분이 걸립니다. Firebase 콘솔의 Firestore 색인 화면에서 새 인덱스가 모두 "사용 설정됨"이 된 것을 확인합니다. 인덱스가 준비되기 전에는 그 인덱스를 쓰는 쿼리(운영자 검토 목록, MyPage "내가 제안한 질문")가 실패합니다. 새 TTL 정책은 TTL 화면에서 상태를 확인합니다. → TTL 정책

4. 기본 질문 시드 ​

bash
cd functions
GOOGLE_CLOUD_PROJECT=<프로젝트 ID> node lib/scripts/seedQuestions.js --dry-run
GOOGLE_CLOUD_PROJECT=<프로젝트 ID> node lib/scripts/seedQuestions.js

src/content/questions.json의 기본 질문 40개(system_opening_01..30, system_followup_01..10)와 질문 배지 3개를 만들거나 맞춥니다.

  • dry-run 출력에서 만들 문서·고칠 필드, 배지 생성 예정 목록을 먼저 확인합니다.
  • 멱등적이라 배포 때마다 실행해도 됩니다. questions.json을 고친 릴리스에서는 꼭 실행합니다. 두 번째 실행은 "created 0, updated 0"이어야 합니다.
  • 운영자가 숨긴 기본 질문은 숨김으로 남고, 이미 있는 배지는 덮어쓰지 않습니다.
  • 시드 전에는 질문으로 쓰기가 앱 안의 목록을 쓰고, 기본 질문과 같은 문구의 제안도 중복으로 걸러지지 않습니다.

→ seedQuestions 스크립트

5. 클라이언트 배포 ​

bash
firebase deploy --only hosting

shareRenderer는 Hosting의 index.html을 템플릿으로 받아 쓰므로 공유 페이지도 새 번들을 가리키게 됩니다.

약관 자리 표시 검사 ​

Hosting 배포 전에 firebase.json의 predeploy가 scripts/checkLegalPlaceholders.js를 실행합니다. npm run build(prerender)가 남긴 dist/.legal-placeholders.json에 채우지 않은 값(운영자, 보호책임자, 시행일 등)이 있으면 배포를 멈춥니다. 프로덕션의 약관·처리방침이 빈 값으로 바뀌고 모든 사용자가 빈 약관에 동의하게 되는 것을 막기 위해서입니다.

  • 값은 src/content/legal.js 한 곳에서 채우고 다시 빌드합니다.
  • 빌드 결과가 없으면(dist/.legal-placeholders.json 없음) 역시 멈춥니다.
  • 스테이징에서만 GRATO_ALLOW_LEGAL_PLACEHOLDERS=1로 건너뛸 수 있습니다. 프로덕션에서는 쓰지 않습니다.

6. 확인 ​

  • 브라우저에서 강력 새로고침 후 화면이 정상으로 나오는지, 로그인이 되는지
  • 글 작성 → 기본이 "나만 보기"인지(Circle이 미리 선택되지 않는지), 홈 "내 기록" 탭에 바로 보이는지, 연속일 카드가 갱신되는지(트리거)
  • "Circle에 공유"로 글 작성 → 그 Circle 탭이 열리는지, Circle 멤버에게 알림이 가는지
  • Circle이 없는 계정 → 홈에 내 기록과 Circle 안내 카드가 함께 보이는지
  • Circle 생성·초대 링크로 참여 → "함께하기" 배지
  • 질문으로 쓰기: 질문 두 개에 답하기(두 번째는 건너뛰기도) → 초안에 제목 입력 → 저장
  • 질문 제안 → MyPage "내가 제안한 질문"에 "검토 중" → 관리자 페이지 "질문"에서 선정 → 제안자에게 알림, "첫 질문 선정" 배지, 상태 "선정됨", 다음 세션의 질문으로 쓰기에 "💡 …님의 질문"
  • 질문 반려(사유) → MyPage에 사유 표시 / 숨기기 → 질문으로 쓰기에서 빠짐
  • 글 공개 → /share/gratitude/{id}가 내용을 보여 주는지, 공개 취소 후 1분 안에 "비공개"로 바뀌는지
  • 2단계 기능의 확인 항목은 이번 릴리스에 있습니다.
  • Cloud Functions 로그에 오류가 없는지 (cd functions && npm run logs)

배포 직후 예전 버전 화면을 열어 둔 브라우저에서는 일부 동작이 실패할 수 있습니다. 새로고침하면 새 버전을 받습니다.

iOS·Android 앱 빌드를 누구에게든(TestFlight, 내부 테스트 포함) 나눠 주기 전에 올립니다. 웹 사용자에게는 달라지는 것이 없습니다. 기본 배포 순서를 따르고, 시드는 필요 없습니다. → iOS·Android 앱: 서버·Hosting 먼저 배포

구분이번에 바뀌는 것
함수utils/messaging.ts: 앱 토큰(platform: ios·android)에 notification 페이로드. sendDailyReminder: 앱이 로컬 알림을 맡은 사용자 건너뜀. 새 함수·삭제되는 함수 없음

콘솔iOS 푸시용 APNs 인증 키 업로드 → APNs 키

확인:

bash
curl -sI https://grato.today/.well-known/apple-app-site-association | grep -i content-type   # application/json
curl -s https://grato.today/.well-known/assetlinks.json                                       # cc.mknw.grato

  • 함수 로그의 sendDailyReminder 줄에 app-local 수가 찍히는지.

이번 릴리스: 2단계 스토어 필수 기능 ​

변경 이력의 릴리스입니다. 서버와 클라이언트가 강하게 맞물려 있어, 기본 배포 순서에 아래 준비와 순서 조정이 더해집니다.

구분이번에 바뀌는 것
함수새 callable moderate, deleteAccount. 새 트리거 onGratitudeDeleted, onReportCreated, onBlockCreated, onPublicNameWritten, onCircleNameWritten. onGratitudeCreated·onCommentCreated·onReactionUpdated에 자동 숨김과 차단 반영, createCircle·joinCircle·submitQuestion에 잠긴 계정 거부. 삭제되는 함수 없음
규칙users.consent, users/{uid}/blocks, reports, disabledUsers(접근 불가), 글·댓글의 moderation(서버만), 글 생성·댓글 생성에 동의·활성 계정 확인, 작성자의 글 삭제, 운영자의 신고 대상 읽기
인덱스reports: (status, createdAt ↓), (status, createdAt ↑), (reporterId, createdAt ↑). comments.userId 컬렉션 그룹 단일 필드
TTLreports.expireAt, disabledUsers.expireAt
데이터1회성 스크립트 없음. 기본 질문도 바뀌지 않아 seedQuestions는 필요 없음
클라이언트Apple 로그인, 동의 화면, 계정 삭제, 신고·차단, 글 삭제, 관리자 "신고" 탭, 약관·처리방침·고객지원·삭제 안내 페이지, 서비스 워커(신고 알림 클릭)
콘솔Apple 로그인 공급업체, Firestore 시점 복구 확인

배포 전 준비 ​

  1. Apple 로그인 설정 — 아래 Apple 로그인 설정. Hosting보다 먼저 해 둬야 새 화면의 "Apple로 계속하기"가 동작합니다.
  2. 약관 값 채우기 — src/content/legal.js의 자리 표시(현재 시행일 EFFECTIVE_DATE)를 채우고 다시 빌드합니다. 남아 있으면 Hosting 배포가 거부됩니다. → 약관 자리 표시 검사
  3. Firestore 시점 복구(PITR) — 개인정보 처리방침이 "장애 복구용 백업(시점 복구, 최대 7일)"을 적고 있으므로, Firebase 콘솔(또는 Google Cloud 콘솔)의 Firestore 데이터베이스 설정에서 시점 복구가 켜져 있는지 확인하고 꺼져 있으면 켭니다.
  4. 운영자 기기 알림 — 운영자 계정(users/{uid}.isAdmin == true)으로 로그인한 기기에서 푸시를 켜 둡니다. 새 신고 알림을 받아야 약관의 "24시간 안에 검토"를 지킬 수 있습니다.
  5. 테스트 4종(클라이언트, 함수 단위, 규칙, 함수 엔드투엔드)과 빌드.

순서 ​

  • 서버 다음에 곧바로 Hosting을 올립니다. 새 규칙은 글·댓글을 만들 때 약관 동의 기록을 요구하는데, 기존 사용자는 새 클라이언트의 동의 화면을 거쳐야 이 기록이 생깁니다. 그래서 규칙 배포와 Hosting 배포 사이에는 기존 사용자의 글·댓글 작성이 거부됩니다. 이 틈을 짧게 하려고 이번에는 인덱스 완료를 기다리지 않고 Hosting을 올립니다.
  • 인덱스가 준비되기 전에도 앱은 동작합니다: 관리자 신고 목록은 클라이언트에서 정렬하고, 신고 도배 판단은 실패해도 신고는 그대로 접수됩니다. 다만 comments.userId 컬렉션 그룹 인덱스가 준비되기 전에는 계정 삭제가 실패합니다(사용자는 오류를 보고 나중에 다시 시도할 수 있음). 인덱스 화면에서 완료를 꼭 확인합니다.
  • 배포 직후 열려 있던 예전 탭에서는 글·댓글 작성이 권한 오류로 실패할 수 있습니다. 새로고침하면 동의 화면이 나옵니다.
  • 모든 기존 사용자가 다음 방문 때 동의 화면을 한 번 봅니다(동의 기록이 없으므로). 새 약관 공지와 시점을 맞춥니다.

Apple 로그인 설정 ​

웹(Firebase JS SDK 팝업)의 Sign in with Apple에 필요한 설정입니다. 키와 ID의 값은 저장소와 문서에 적지 않습니다. 비공개 키(.p8) 파일은 내려받을 수 있는 기회가 한 번뿐이므로 저장소 밖 안전한 곳에 보관합니다.

Apple Developer (Certificates, Identifiers & Profiles)

  1. App ID: 앱의 기본 App ID에 Sign in with Apple 기능을 켭니다(3단계 iOS 앱도 이 App ID를 씁니다).
  2. Services ID: 웹 로그인용 Services ID를 만들고 Sign in with Apple을 켠 뒤 설정합니다.
    • Primary App ID: 위 App ID
    • Domains and Subdomains: 로그인 도메인(.env의 VITE_FIREBASE_AUTH_DOMAIN, 커스텀 도메인)과 Firebase 기본 인증 도메인(<프로젝트 ID>.firebaseapp.com)
    • Return URLs: https://<로그인 도메인>/__/auth/handler와 https://<프로젝트 ID>.firebaseapp.com/__/auth/handler(Android 앱의 Apple 로그인이 이 주소로 돌아옵니다)
  3. Key: Sign in with Apple을 켠 키를 만들고 .p8 파일을 내려받습니다. Key ID와 Team ID를 확인해 둡니다.

Firebase 콘솔 › Authentication › 로그인 방법

  1. 새 공급업체 Apple을 사용 설정하고 Services ID를 입력합니다.
  2. OAuth 코드 흐름 구성에 Apple Team ID, Key ID, 비공개 키를 입력합니다. 콘솔에는 "선택사항"으로 나오지만 웹과 Android의 Apple 로그인에는 필수입니다. 빠지면 Firebase가 OPERATION_NOT_ALLOWED: Code flow is not enabled for Apple로 거부하고, 로그인 화면에 "지금은 이 방법으로 로그인할 수 없어요"가 나옵니다(iOS 앱의 네이티브 로그인만 이 설정 없이 됩니다). 계정 삭제 때 Apple 연결 해제(토큰 폐기)에도 쓰입니다.
    • 확인: 웹 API 키로 accounts:createAuthUri(providerId: "apple.com")를 호출해 appleid.apple.com 주소가 오면 됩니다.
  3. 승인된 도메인에 로그인 도메인과 서비스 도메인이 있는지 확인합니다(Google 로그인 때 이미 등록).
  4. "이메일 주소당 계정 하나" 설정은 그대로 둡니다. 다른 수단으로 이미 가입한 이메일이면 앱이 처음 가입한 방법으로 로그인하라고 안내합니다.
  • Grato는 Apple 사용자에게 이메일을 보내지 않으므로 Apple의 비공개 이메일 릴레이용 발신 도메인 등록은 지금은 필요 없습니다. 이메일을 보내게 되면 다시 검토합니다.
  • 확인: 데스크톱 Chrome과 iPhone Safari에서 "Apple로 계속하기" → 처음 가입이면 동의 화면 → 홈의 "이름을 알려주세요" 카드. "이메일 가리기"로도 가입해 봅니다.

확인 ​

기본 확인 항목에 더해:

  • 기존 계정으로 로그인 → 동의 화면("새 이용약관을 확인해주세요") → 동의 후 원래 화면, 다시 열면 묻지 않음
  • 새 이메일 가입(체크리스트), Google·Apple 가입 → 동의, 만 14세 미만 선택 → 계정이 지워지고 로그인 화면 안내
  • /terms, /privacy, /support, /account-deletion이 로그인 없이 열리고 자리 표시가 없는지
  • 다른 계정의 Circle 글·댓글 신고 → 운영자 기기에 푸시 → 관리자 "신고" 탭에서 미리보기, 숨기기 → 작성자에게 "검토 중이에요", 다른 멤버 피드에서 빠짐 → 숨김 해제로 복구
  • 차단 → 그 사람의 글·댓글이 사라지고 알림이 오지 않음, 대기열에 차단 신고(푸시 없음), MyPage › 설정 › 차단한 사용자에서 해제
  • 욕설이 든 Circle 글 → 바로 숨김, Circle 알림 없음, 대기열에 자동 신고
  • 내 글 삭제 → 피드에서 사라지고 댓글도 삭제, 연속일·이번 달 수가 다시 계산됨
  • 테스트 계정으로 계정 삭제(Google, Apple 각각) → 로그인 화면 "계정을 삭제했어요", 관리하던 Circle이 다른 멤버에게 넘어감, Apple ID 설정에서 Grato가 사라짐
  • Cloud Functions 로그에 deleteAccount, moderate, 새 트리거 오류가 없는지

1단계 릴리스의 1회성 작업 ​

1단계(2026-10-07) 릴리스를 배포할 때 함께 실행한 작업입니다. 이후 배포에서는 필요 없습니다. 두 스크립트 모두 멱등적이라, 실행했는지 확실하지 않으면 dry-run으로 확인합니다.

이름 선점 백필 ​

bash
cd functions
GOOGLE_CLOUD_PROJECT=<프로젝트 ID> node lib/scripts/backfillPublicNames.js --dry-run
GOOGLE_CLOUD_PROJECT=<프로젝트 ID> node lib/scripts/backfillPublicNames.js

1단계 규칙은 이름 선점(publicNames)을 가진 사용자만 그 이름을 프로필에 쓸 수 있게 합니다. 그래서 규칙을 올리기 전에 기존 사용자의 선점을 만들고, 배포 뒤에 한 번 더 실행해 그사이 예전 클라이언트가 만든 프로필도 선점을 갖게 했습니다. dry-run 출력에서 생성 예정 수와 같은 이름을 공유하는 프로필 목록을 먼저 확인하세요.

AI 글쓰기 데이터 정리 ​

bash
cd functions
GOOGLE_CLOUD_PROJECT=<프로젝트 ID> node lib/scripts/purgeAiData.js --dry-run
GOOGLE_CLOUD_PROJECT=<프로젝트 ID> node lib/scripts/purgeAiData.js

AI 글쓰기 기능을 없앤 릴리스를 처음 배포한 뒤 한 번 실행합니다. dry-run으로 컬렉션별 문서 수를 확인한 뒤 실제로 지웁니다. 지운 데이터는 되돌릴 수 없습니다. 한 번 더 실행해 모두 0개인지 확인합니다. → purgeAiData 스크립트

더 이상 쓰는 함수가 없는 비밀값도 정리합니다. 함수 배포에서 generateGratitude가 삭제된 것을 확인한 뒤 firebase functions:secrets:destroy GEMINI_API_KEY로 비밀값을 지우고, 키를 발급한 콘솔에서 API 키 자체도 삭제합니다.

배포 중 나오는 확인 프롬프트 ​

프롬프트의미응답
코드에 없는 함수를 삭제할지콘솔에는 있지만 코드에서 빠진 함수. 1단계 릴리스에서는 checkBadges(배지 평가가 onGratitudeCreated 파이프라인으로 통합됨), migrateBadgeIds(1회성 이전 함수), generateGratitude·generateQuestion(AI 글쓰기 기능 제거)이 대상이었음삭제 대상이 의도한 함수뿐인지 확인하고 삭제(y). 질문 제안 릴리스와 2단계 릴리스는 함수를 지우지 않으므로, 이 프롬프트가 나오면 아니오(n) 후 원인을 확인
Storage 규칙이 Firestore에 접근할 권한 부여circlePhotos 규칙이 firestore.get()으로 Circle 관리자를 확인하는 cross-service 규칙이라 필요허용(y). 거부하면 Circle 사진 업로드가 모두 실패
인덱스 삭제 여부콘솔에만 있고 firestore.indexes.json에 없는 인덱스·필드 재정의내용을 확인한 뒤 결정. 모르면 아니오. 예전 AI 글쓰기 컬렉션(aiCache, aiUsage)의 TTL 정책만 남아 있다면 삭제해도 됩니다

처음 배포하는 callable·트리거(2단계의 moderate, deleteAccount와 새 트리거 5개 포함)는 권한 설정 때문에 몇 분 뒤부터 정상 동작할 수 있습니다.

firestore.indexes.json의 fieldOverrides에 "ttl": true로 선언되어 firestore 배포 때 적용됩니다.

컬렉션필드쓰는 쪽에서 정하는 보관 기간

  • TTL 정책은 처음 만들 때 활성화까지 시간이 걸릴 수 있습니다. Firebase 콘솔의 Firestore TTL 화면에서 상태를 확인하세요.
  • 삭제 시점은 만료 직후가 아니라 보통 24시간 이내입니다. 만료 판단이 중요하다면 코드에서도 expireAt을 확인합니다.
  • 새 TTL 컬렉션을 추가하면 fieldOverrides와 데이터 모델을 함께 갱신합니다.

롤백 ​

  • 세트로 되돌립니다. 클라이언트·함수·규칙 중 하나만 이전 버전으로 돌리면 서로의 기대가 어긋납니다. 되돌릴 때도 이전 커밋을 체크아웃해 같은 순서로 빌드·배포합니다.
  • Hosting: Firebase 콘솔 Hosting의 출시 기록에서 이전 버전으로 즉시 되돌릴 수 있습니다. 다만 함수·규칙과 짝이 맞는지 먼저 확인하세요.
  • 규칙: 콘솔의 규칙 기록에서 이전 버전을 볼 수 있지만, 저장소 파일을 기준으로 다시 배포하는 것을 원칙으로 합니다.
  • 함수: 이전 커밋에서 firebase deploy --only functions. 이번에 삭제한 함수는 이전 코드로 배포하면 다시 생깁니다.
  • 데이터: publicNames 선점 문서, 새 필드(removedIds, sharedAt 등), 질문 컬렉션(questions, questionOriginals, questionQuota, adminAuditLogs)과 질문 배지는 이전 버전에서 무시되므로 지우지 않아도 됩니다. 이전 규칙에는 질문 컬렉션의 match가 없어 클라이언트 접근이 기본 거부됩니다. purgeAiData로 지운 데이터는 롤백해도 돌아오지 않습니다.
  • 질문 제안 릴리스를 되돌리면 작성 화면은 다시 예전 Circle 선택을 쓰고, 홈의 "내 기록" 탭과 질문 제안·검토 화면이 사라집니다. 이미 쓴 개인 글은 그대로 남습니다.
  • 2단계 릴리스를 되돌리면 이전 규칙에는 reports·blocks·disabledUsers의 match가 없어 클라이언트 접근이 기본 거부되고, 글 삭제도 다시 막힙니다. 이미 쓴 users.consent, 신고, 차단 문서는 무시되므로 지우지 않아도 됩니다. 숨김 처리된 Circle 글은 groupId가 비어 있어 이전 버전에서 개인 글처럼 보이므로, 되돌리기 전에 관리자 화면에서 숨김을 해제할지 정합니다. 이미 삭제한 계정·글은 돌아오지 않습니다.

문서 사이트 자동 배포 ​

이 문서는 docs/가 바뀐 커밋이 main에 올라가면 GitHub Actions(.github/workflows/docs.yml)가 자동으로 배포합니다.

  • 소스 저장소는 비공개이고, 빌드 결과(docs/.vitepress/dist)만 공개 저장소 subongjeong/grato-docs의 gh-pages 브랜치로 올라갑니다.
  • 인증은 공개 저장소에만 등록된 쓰기용 배포 키(비밀값 이름 DOCS_DEPLOY_KEY)를 씁니다.
  • 공개 저장소의 커밋 메시지는 항상 docs: deploy로 고정해 비공개 저장소의 커밋 메시지가 노출되지 않게 합니다.
  • 깨진 내부 링크가 있으면 빌드가 실패해 배포되지 않습니다. 수동 실행(workflow_dispatch)도 가능합니다.
