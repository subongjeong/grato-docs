테스트 ​

테스트는 네 묶음입니다. 모두 Node 내장 node:test를 씁니다.

묶음위치명령필요 조건
클라이언트 단위src/**/*.test.jsnpm test (루트)없음
배포 스크립트 단위scripts/**/*.test.mjs (함수 삭제 방지 비교, 변경 이력 조각 합치기, 앱 버전·Xcode Cloud 스크립트 appVersion.test.mjs, Android 릴리스 워크플로와 build.gradle 서명 설정 androidRelease.test.mjs)npm test (루트, 클라이언트와 함께)없음
함수 단위functions/src/test/*.test.tscd functions && npm test없음 (tsc 후 lib/test 실행)
보안 규칙tests/rules/test/*.test.jscd tests/rules && npm testFirebase CLI, JDK 21
함수 엔드투엔드functions/src/e2e/*.e2e.tscd functions && npm run test:e2eFirebase CLI, JDK 21

배포 전에는 네 묶음을 모두 통과시키고, 문서를 고쳤다면 cd docs && npm run build도 확인합니다(깨진 링크가 있으면 실패).

PR을 올리면 GitHub Actions가 같은 테스트를 자동으로 돌립니다 → CI 테스트

CI 테스트 (PR마다) ​

.github/workflows/test.yml(Test)이 모든 PR과 main push에서 돕니다. 배포하지 않고, 비밀값·Google 자격 증명을 쓰지 않습니다(에뮬레이터는 demo-grato, 웹 빌드는 저장소의 .env.emulator). → ADR-36

job하는 일PR에서 도는 때 (바뀐 경로)
Changed paths바뀐 파일로 아래 job을 고름항상
Web — test and buildnpm ci · npm test · vite build --mode emulator + prerenderdocs/·marketing/·tests/rules/만 바뀐 게 아니면 (ios/·android/도 돎: 버전·Xcode Cloud 스크립트 테스트)
Functions — build and testfunctions에서 npm ci · npm run build · npm testfunctions/, src/content/, firestore.rules
Security rules (emulator)JDK 21 + Firebase CLI(deploy.yml과 같은 고정 버전), tests/rules에서 npm ci · npm testfirestore.rules, storage.rules, firestore.indexes.json, tests/rules/
Functions — e2e (emulator)JDK 21 + Firebase CLI, functions에서 npm run test:e2e함수 job과 같음
Docs — build (dead links)node scripts/mergeChangelog.mjs --check(변경 이력 조각), docs에서 npm ci · npm run builddocs/, 변경 이력 스크립트
Test summary위 job 결과를 표로 요약. 하나라도 실패·취소면 실패, 건너뛴 job은 통과로 봄항상
  • test.yml 자체를 고치거나 main에 push하면 모든 job이 돕니다(경로 필터가 놓친 의존을 잡음).
  • 함수 엔드투엔드도 필수입니다(요약에 포함). 에뮬레이터 안에서만 돌고 외부 서비스를 부르지 않아 결과가 안정적이라고 봅니다. 자꾸 이유 없이 실패하면 job에 continue-on-error: true를 달고 요약에서 빼는 것을 검토합니다.
  • 에뮬레이터 jar는 ~/.cache/firebase/emulators를 Firebase CLI 버전 키로 캐시합니다. deploy.yml의 FIREBASE_TOOLS_VERSION을 올리면 test.yml도 같이 올립니다.
  • 같은 PR에 새 커밋을 올리면 앞의 실행은 취소됩니다.
  • 이 웹 빌드(dist/)는 검사용이라 배포하지 않습니다. 배포 빌드는 CI로 배포가 따로 만듭니다.
  • Test가 통과한 같은 저장소 PR은 Preview 워크플로가 stg(grato-stg) 웹 설정으로 다시 빌드해 stg Hosting 미리보기 채널에 올립니다 → PR 웹 미리보기

필수 검사로 지정하기 (오너) ​

실패한 PR을 병합 버튼에서 막으려면 오너가 저장소 설정에서 한 번 지정합니다.

  1. GitHub 저장소 → Settings → Rules → Rulesets → New ruleset → New branch ruleset (또는 Branches → 브랜치 보호 규칙)
  2. 대상 브랜치: main(Default branch), Enforcement: Active
  3. Require status checks to pass 켜기 → Add checks에서 Test summary 선택(목록에 없으면 Test가 한 번 돈 뒤에 나타남). 필요하면 Require branches to be up to date before merging
  4. 저장. 이제 Test summary가 초록이어야 병합 버튼이 열립니다.

Test summary 하나만 지정합니다. 경로 때문에 건너뛴 job을 필수로 지정하면 그 PR은 "기다리는 중"으로 남아 병합할 수 없습니다.

보안 규칙 테스트 ​

tests/rules/는 별도 npm 패키지입니다(@firebase/rules-unit-testing, firebase).

bash
cd tests/rules
npm install          # 처음 한 번
npm test             # JAVA_HOME이 JDK 21을 가리켜야 함

npm test는 다음을 순서대로 합니다.

  1. pretest: 루트의 firestore.rules, storage.rules, firestore.indexes.json을 .rules/로 복사
  2. firebase emulators:exec --project demo-grato --only firestore,storage로 에뮬레이터를 띄우고
  3. node --test --test-concurrency=1 "test/*.test.js" 실행 후 에뮬레이터 종료

포트는 tests/rules/firebase.json에 고정되어 있어(Firestore 8180, Storage 9198, Hub 4410 등) 개발용 에뮬레이터와 동시에 띄워도 충돌하지 않습니다.

  1. 필요한 데이터가 test/helpers.js의 seed()에 없으면 추가합니다. 모든 테스트가 같은 세계를 공유합니다.

    픽스처내용

  2. 컬렉션의 describe 안에 it을 추가합니다. 허용은 assertSucceeds, 거부는 이름을 DENY:로 시작하고 assertFails를 씁니다.

    js
    it('DENY: a non-member reacts to a circle gratitude', async () => {
  await assertFails(updateDoc(ref('carol', 'gratitudes/groupBob'), {
    [`reactions.${HEART}`]: arrayUnion('carol'),
  }))
})

    ref(uid, path)는 해당 사용자로 인증된 문서 참조, ref(null, path)는 비로그인입니다. 서버 동작을 흉내 낼 때는 asServer(testEnv, fn)(규칙 비활성)을 씁니다.

  3. 규칙을 고쳤다면 거부 테스트가 실제로 실패를 잡는지 확인합니다. firestore.rules와 storage.rules를 복사한 디렉터리에서 검사 하나를 일부러 약하게 만들고, 그 디렉터리를 GRATO_RULES_DIR로 지정해 테스트가 실패하는지 봅니다.

    bash
    GRATO_RULES_DIR=/tmp/weak-rules npm test   # 이번에는 실패해야 정상

  4. 교차 읽기(get()) 수가 바뀌었다면 보안 규칙의 예산 표도 갱신합니다.

자동 테스트 (npm run test:e2e) ​

2단계의 서버 동작은 함수 에뮬레이터에서 자동으로 확인합니다.

bash
cd functions && npm run test:e2e  # 함수 빌드 후 에뮬레이터에서 실행. JAVA_HOME이 JDK 21을 가리켜야 함
  • functions/firebase.e2e.json으로 Functions·Firestore·Auth·Storage 에뮬레이터를 demo-grato 프로젝트, 전용 포트(Firestore 8280, Auth 9399, Functions 5301, Storage 9398 등)로 띄워 다른 에뮬레이터와 충돌하지 않습니다. Storage 규칙은 functions/e2e.storage.rules.
  • Admin SDK로 데이터를 넣고, Auth 에뮬레이터의 ID 토큰으로 callable을 HTTP로 부릅니다. demo- 프로젝트와 에뮬레이터 환경이 아니면 건너뜁니다.

직접 확인 ​

클라이언트 화면과 공유 페이지는 에뮬레이터에서 직접 확인합니다.

bash
npm run build && (cd functions && npm run build)
firebase emulators:start --project demo-grato --only auth,firestore,functions,storage,tasks,hosting

기본 포트: Auth 9099, Firestore 8080, Functions 5001, Storage 9199, Cloud Tasks 9499(첫 나눔 리더 알림 firstShareFollowup), Hosting 5000, Emulator UI 4000. macOS에서는 AirPlay 수신 모드가 5000번 포트를 쓰므로, Hosting 에뮬레이터가 뜨지 않으면 시스템 설정에서 AirPlay 수신 모드를 끕니다.

  • 트리거(onGratitudeCreated 등)는 Emulator UI에서 문서를 만들거나 스크립트로 쓰면 실행되고, 로그는 UI의 Logs 탭에서 봅니다.

Circle 흐름을 확인하는 예시 스크립트(저장소 루트에서 임시로 실행, 커밋하지 않음):

js
// e2e-circles.mjs
import { initializeApp } from 'firebase/app'
import { getAuth, connectAuthEmulator, createUserWithEmailAndPassword } from 'firebase/auth'
import { getFunctions, connectFunctionsEmulator, httpsCallable } from 'firebase/functions'

function client(name) {
  const app = initializeApp({ apiKey: 'demo', projectId: 'demo-grato' }, name)
  const auth = getAuth(app)
  connectAuthEmulator(auth, 'http://127.0.0.1:9099', { disableWarnings: true })
  const fns = getFunctions(app, 'asia-northeast3')
  connectFunctionsEmulator(fns, '127.0.0.1', 5001)
  return { auth, call: (n, d) => httpsCallable(fns, n)(d).then((r) => r.data) }
}

const alice = client('alice')
const bob = client('bob')
await createUserWithEmailAndPassword(alice.auth, `alice${Date.now()}@example.com`, 'password')
const b = await createUserWithEmailAndPassword(bob.auth, `bob${Date.now()}@example.com`, 'password')

const { groupId, inviteCode } = await alice.call('createCircle', { name: '테스트' })
console.log(await bob.call('joinCircle', { code: inviteCode }))          // alreadyMember: false
await alice.call('removeCircleMember', { groupId, memberId: b.user.uid })
await bob.call('joinCircle', { code: inviteCode }).catch((e) => console.log(e.code, e.message))
await alice.call('unbanCircleMember', { groupId, memberId: b.user.uid })
console.log(await bob.call('joinCircle', { code: inviteCode }))          // 다시 참여
process.exit(0)

질문 제안 흐름도 같은 방식으로 확인합니다.

  1. 기본 질문을 에뮬레이터에 넣습니다: cd functions && FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 GOOGLE_CLOUD_PROJECT=demo-grato node lib/scripts/seedQuestions.js
  2. 위 스크립트처럼 사용자를 만들고 submitQuestion({ text, kind })를 부릅니다. 한도·필터·중복 오류 메시지도 여기서 확인합니다.
  3. Emulator UI에서 운영자로 쓸 사용자의 users/{uid}에 isAdmin: true를 넣고, 그 사용자로 reviewQuestion({ id, action: 'approve' })를 부릅니다.
  4. 질문 문서의 상태와 approvedAt, adminAuditLogs, 제안자의 userBadges(questions_selected_1), notificationLogs/question_selected_{id}를 확인합니다.
