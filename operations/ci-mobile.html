앱 빌드 CI (iOS·Android) ​

한 번에 바꾸는 스크립트(scripts/bumpVersion.mjs, 순수 로직은 scripts/lib/appVersion.mjs와 테스트):

bash
npm run version:bump -- --show                         # 지금 값
npm run version:bump -- --version 1.0.2 --build 6       # iOS 앱·위젯 + Android 모두
npm run version:bump -- --version 1.0.2 --allow-same    # 보이는 버전만 (빌드 번호 그대로)
npm run version:bump -- --build 7 --platform ios        # 한 플랫폼만 (ios | android)
npm run version:bump -- --version 1.0.2 --build 6 --dry-run
  • 빌드 번호는 올라가기만 합니다(같은 번호는 --allow-same일 때만). 보이는 버전은 내려가지 않습니다.
  • 앱과 위젯의 값이 서로 다르거나, 빌드 설정 수(앱·위젯 × Debug·Release = 4)가 다르면 아무것도 쓰지 않고 멈춥니다.
  • 바꾼 파일(project.pbxproj, android/app/build.gradle)은 PR로 커밋합니다.

CI가 붙이는 빌드 번호와의 관계

  • iOS: Xcode Cloud가 빌드마다 번호(CI_BUILD_NUMBER)를 붙이고, TestFlight에 그 번호로 올라갑니다. ci_pre_xcodebuild.sh가 앱·위젯의 CURRENT_PROJECT_VERSION을 그 번호로 맞춥니다(커밋하지 않음). 저장소에 커밋된 번호는 손으로 마지막에 올린 번호(지금 5)이고, Xcode Cloud 번호는 이보다 커야 합니다 — 작거나 같으면 빌드가 멈춥니다. 그래서 App Store Connect에서 "다음 빌드 번호"를 6 이상으로 정합니다(설정 6).
  • Xcode Cloud를 쓰는 동안 저장소의 iOS 빌드 번호는 올리지 않아도 됩니다. 다시 맥에서 손으로 올릴 일이 생기면 먼저 npm run version:bump -- --platform ios --build <마지막 Xcode Cloud 번호 + 1>로 올리고 커밋합니다.
  • Android: 워크플로가 실행마다 versionCode를 정합니다 — 입력 versionCode가 있으면 그 값, 없으면 실행 번호 + ANDROID_VERSION_CODE_OFFSET(변수, 기본 5. 첫 실행이 6). 커밋된 versionCode(지금 5, 손으로 마지막에 올린 번호)보다 커야 하고, 아니면 bumpVersion.mjs가 멈춥니다. 바꾼 값은 그 실행 안에서만 쓰고 커밋하지 않습니다. 실행 번호는 실패·거절된 실행에도 늘어나므로 번호가 건너뛸 수 있습니다(문제 없음, 올라가기만 함). 다시 맥에서 손으로 올릴 때는 먼저 npm run version:bump -- --platform android --build <마지막 CI 번호 + 1>.
  • iOS와 Android의 빌드 번호는 서로 달라도 됩니다(스토어가 따로 셈).
  • 보이는 버전(1.0.2 등)은 CI가 바꾸지 않습니다. 새 버전을 낼 때 스크립트로 올려 PR로 병합한 뒤 CI 빌드를 시작합니다.

저장소에 있는 것:

파일하는 일

ios/App/ci_scripts/ci_pre_xcodebuild.sh매 xcodebuild 전. CI_BUILD_NUMBER가 커밋된 빌드 번호보다 큰지 확인하고 앱·위젯 4곳의 CURRENT_PROJECT_VERSION을 그 번호로. 앱·위젯 버전이 다르면 멈춤. Node 없이 sh·sed만 씀
ios/App/App.xcodeproj/xcshareddata/xcschemes/App.xcscheme공유 scheme App(Xcode Cloud는 공유 scheme만 봄). Archive는 Release
…/project.xcworkspace/xcshareddata/swiftpm/Package.resolvedXcode Cloud는 패키지를 자동으로 풀지 않고 이 파일만 씁니다. 커밋된 상태여야 합니다
  • 두 스크립트는 실행 권한이 있어야 합니다(chmod +x, 없으면 Xcode Cloud가 zsh로 실행). 테스트(scripts/appVersion.test.mjs)가 권한·shebang·빌드 번호 처리를 확인합니다.
  • cap sync와 SPM: Capacitor 8은 SPM을 쓰고, cap sync가 ios/App/CapApp-SPM/symlinks/(Git 제외)를 만듭니다. 이 링크가 있어야 패키지를 풀 수 있어서 cap sync는 반드시 post-clone에서 합니다(Xcode Cloud가 패키지를 받는 단계보다 앞). 플러그인을 더하거나 올리면 맥에서 npm run build && npx cap sync ios → Xcode에서 패키지 갱신 → Package.swift·Package.resolved·project.pbxproj를 커밋합니다. 커밋하지 않으면 CI가 멈춥니다.
  • 로컬 확인: GRATO_CI_DRY_RUN=1 VITE_FIREBASE_...=… sh ios/App/ci_scripts/ci_post_clone.sh(Homebrew·cap sync 건너뜀, PATH의 Node 22 사용), CI_BUILD_NUMBER=6 GRATO_PBXPROJ=<사본> sh ios/App/ci_scripts/ci_pre_xcodebuild.sh.

Xcode 26 기준입니다. 메뉴 이름은 Xcode 버전에 따라 조금 다를 수 있습니다.

2026-10-18 설정 완료, 첫 빌드 성공. 오너가 GitHub 릴리스로 release/ios-1.0.1-6 태그를 만들자 빌드가 자동으로 시작됐습니다. 빌드 6은 Archive 약 6분, 오류 0, 경고 8(플러그인 컴파일 경고)로 끝났고 TestFlight 내부 테스트에 올라갔습니다. GitHub 커밋 화면에도 Xcode Cloud 체크로 결과가 보입니다. 설정한 것:

  • 다음 빌드 번호 6.
  1. 이 PR이 병합된 main을 맥에 받기 → npx cap open ios(Xcode에서 ios/App/App.xcodeproj). scheme 목록에 App이 둘이면 Product › Scheme › Manage Schemes에서 Shared가 아닌 것을 지웁니다.

    • Actions: 기본 Build를 지우고 Archive 하나: Platform iOS, Scheme App, Distribution Preparation: App Store Connect(예전 이름 "TestFlight and App Store"). ("TestFlight (Internal Testing Only)"로 만든 빌드는 App Store 심사에 낼 수 없습니다.) Scheme 옆에 "Scheme 'App' may only exist locally" 경고가 떠도, 공유 scheme이 main에 커밋돼 있으면 그대로 둡니다. Xcode Cloud가 저장소를 아직 한 번도 읽지 않아서 뜨는 경고입니다.

워크플로 › Environment › Environment Variables. 값은 운영 .env와 같습니다. 이 저장소·문서에는 이름만 둡니다.

Android: GitHub Actions → Play 테스트 트랙 ​

  • 시작 방법 두 가지 (둘 다 오너만):
    • 태그 push (권장): main에 병합된 커밋에 android-v<versionName>-<versionCode> 태그를 달아 push합니다. 예: git checkout main && git pull && git tag android-v1.0.1-6 && git push origin android-v1.0.1-6. 태그의 versionName이 android/app/build.gradle과 다르거나, 태그 커밋이 main에 없거나, 형식이 틀리면 첫 단계에서 멈춥니다. 태그로 시작하면 항상 internal·completed입니다.
    • 손으로: Actions → Android release → Run workflow(브랜치 main). 아래 입력을 고를 수 있습니다.
    • main도 android-v* 태그도 아니면 첫 단계에서 실패합니다. 실패한 태그는 git push origin :refs/tags/<태그>로 지우고 고쳐서 다시 답니다(같은 versionCode는 Play가 한 번만 받으므로, 업로드까지 간 번호는 다시 쓰지 않음).
  • 프로덕션 출시: 내부 테스트에서 확인한 뒤 Play Console › 프로덕션 › 출시 승격(내부 테스트 → 프로덕션)으로 같은 AAB를 냅니다. 워크플로는 프로덕션 트랙을 쓰지 않습니다.
  • 입력(손으로 시작할 때): versionCode(비우면 실행 번호 기반), track = internal(내부 테스트, 기본) 또는 alpha(비공개 테스트 — 개인 계정의 12명·14일 테스트용), status = completed(테스터에게 바로) 또는 draft(Play Console에서 손으로 출시). 프로덕션 트랙은 고를 수 없습니다. 심사 제출·스토어 문구는 건드리지 않습니다(출시 노트도 넣지 않음).
  • 오너만 시작: job은 Environment production(운영 비밀값, 배포 규칙 main 브랜치 + android-v* 태그)에서 돕니다. 필수 승인자는 없어서(비공개 저장소 무료 플랜, GRATO-64) 시작하는 순간 출시가 진행됩니다. 웹 운영 배포처럼 오너만 Run workflow를 누르거나 릴리스 태그를 push하고, 에이전트는 시작하지 않고 android-v* 태그도 push하지 않습니다.
  • 빌드: JDK 21, Node 22, 러너의 Android SDK(라이선스 수락, platform 36), npm ci && npm test && npm run build(운영 VITE_*, 테스트 날짜 없이) → 테스트 날짜·약관 자리 표시 검사 → npx cap sync android → ./gradlew bundleRelease.
  • 서명: 비밀값의 업로드 키를 러너 임시 폴더에 풀고(umask 077), android/app/build.gradle이 환경 변수 GRATO_UPLOAD_STORE_FILE·GRATO_UPLOAD_STORE_PASSWORD·GRATO_UPLOAD_KEY_ALIAS·GRATO_UPLOAD_KEY_PASSWORD로 서명합니다. 맥에서는 지금처럼 android/keystore.properties(있으면 이쪽이 우선) → 출시 서명. 빌드 뒤 jarsigner -verify로 서명을 확인하고, 서명한 인증서 SHA-256을 실행 요약에 적습니다(Play Console › 앱 무결성 › 업로드 키와 같아야 함). 키 파일은 마지막에 지웁니다.
  • AAB 아티팩트: grato-<버전>-<versionCode>.aab를 30일 보관합니다. 업로드가 실패해도 이 파일을 Play Console에 손으로 올릴 수 있습니다.
  • 업로드 도구: r0adkll/upload-google-play를 커밋 SHA로 고정(v1.1.5). Play Developer API의 edit(번들 올리기 → 트랙 지정 → 커밋)만 하는 단일 단계라 Ruby·Gemfile이 필요 없고, 스토어 등록 정보(문구·이미지)를 다루는 기능을 쓰지 않습니다. fastlane supply는 같은 일을 하지만 Ruby·bundler 설치와 Gemfile.lock 관리가 늘고, 등록 정보 동기화 기능이 있어 실수로 스토어 문구를 바꿀 위험이 있어 고르지 않았습니다.
  • 동시 실행: concurrency: android-release로 하나씩. 진행 중인 업로드를 끊지 않습니다.

설정 (오너, 한 번) ​

1. Play Developer API 서비스 계정

  1. Google Cloud 콘솔(Firebase와 같은 프로젝트여도 됨) › API 및 서비스 › Google Play Android Developer API 사용 설정
  2. IAM › 서비스 계정 › 만들기 play-upload(역할은 주지 않음) → 키 › 새 키 › JSON → 내려받은 파일은 저장소·문서에 두지 않음
  3. Play Console › 사용자 및 권한 › 새 사용자 초대 → 서비스 계정 이메일, 앱 권한: Grato만, 권한은 "테스트 트랙에 앱 출시"(Release apps to testing tracks)와 "앱 정보 보기(읽기 전용)"만. 프로덕션 출시·스토어 등록 정보 관리 권한은 주지 않습니다.
  4. GitHub › Settings › Environments › production › Secrets PLAY_SERVICE_ACCOUNT_JSON = JSON 파일 내용 전체. 넣은 뒤 내려받은 파일은 지웁니다(분실 시 새 키를 만들고 예전 키를 삭제).

2. 업로드 키 비밀값 4개 (Environment production › Secrets)

이름값
ANDROID_UPLOAD_KEYSTORE_BASE64업로드 키 파일을 base64로: base64 -i <업로드 키 파일> | pbcopy(맥) 붙여 넣기
ANDROID_UPLOAD_STORE_PASSWORD키 저장소 비밀번호
ANDROID_UPLOAD_KEY_ALIAS키 별칭
ANDROID_UPLOAD_KEY_PASSWORD키 비밀번호

값은 android/keystore.properties와 같습니다. 클립보드는 붙여 넣은 뒤 비웁니다.

3. 태그 배포 규칙: GitHub › Settings › Environments › production › Deployment branches and tags → Add deployment branch or tag rule → Ref type Tag, 이름 패턴 android-v*. 이 규칙이 없으면 태그 push 실행이 "environment protection rules" 오류로 멈춥니다(지금 규칙은 main 브랜치만).

4. 변수(선택): ANDROID_VERSION_CODE_OFFSET — 실행 번호에 더할 수(기본 5). 이미 손으로 더 큰 versionCode를 올렸다면 그보다 커지게 정합니다.

웹 설정 VITE_* 일곱 개는 CI로 배포에서 이미 production에 넣은 운영 값을 그대로 씁니다(스토어 빌드는 운영 프로젝트만. stg 앱 변형은 아직 없음, 환경).

5. 첫 실행: 태그 push(예: android-v1.0.1-6) 또는 Run workflow(internal) → 실행 요약의 버전·SHA-256 확인. Play 앱이 아직 한 번도 출시되지 않은 상태(대시보드 "앱 초안")면 status: draft로 돌리고 Play Console에서 손으로 출시합니다(completed는 아래 오류) → Play Console › 테스트 › 내부 테스트에 새 출시가 보이는지 → 테스터 기기에서 업데이트 확인.
