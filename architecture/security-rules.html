보안 규칙 ​

firestore.rules와 storage.rules가 클라이언트가 할 수 있는 일의 전부를 정합니다. 이 문서는 규칙의 설계 원칙과 이유를 설명합니다. 컬렉션별 필드는 데이터 모델을 보세요.

멤버십은 callable로만 ​

text
groups:      create, delete → 거부 / update → 관리자의 name·description·photoURL만
             get → 멤버, 또는 운영자(신고된 Circle 확인, list는 불가)
inviteCodes: get만 (list·쓰기 거부)
users:       groupIds·isAdmin 변경 거부, 생성 시 groupIds는 빈 배열만, delete 거부

이유. 초대 코드로 참여하려면 "코드가 존재하고 만료되지 않았으며 사용 횟수와 정원이 남았고, 내보낸 사용자가 아니며, 사용자의 Circle 수가 한도 아래"를 한 번에 확인하고 groups·users·inviteCodes 세 문서를 원자적으로 바꿔야 합니다. 규칙만으로는 이 검증과 원자성을 보장하기 어려워, 멤버십 변경은 트랜잭션을 쓰는 callable 함수로 옮겼습니다. → Circle, 결정 기록 #3

작성자 필드 검증 ​

글(gratitudes)과 댓글을 만들 때 규칙이 publicProfiles/{auth.uid}를 읽어 다음을 비교합니다.

text
authorName       == profile.displayName
authorTag        == profile.tag
authorPublicName == profile.publicName
authorPhotoURL   == profile.photoURL (없으면 null)

작성자 정보를 글에 복사해 두는 이유는 피드를 그릴 때 작성자마다 프로필을 다시 읽지 않기 위해서입니다(비정규화). 복사본이 원본과 같다는 것을 생성 시점에 규칙이 보장합니다. 클라이언트는 쓰기 직전에 항상 프로필을 다시 읽습니다(getAuthorFields).

공개 프로필과 이름의 유일성 ​

  • publicProfiles는 {displayName, tag, publicName, photoURL} 4개 필드만, publicName == displayName + " #" + tag.
  • tag는 한 번 정해지면 바뀌지 않습니다.
  • photoURL은 본인 Storage 경로(profilePhotos/{uid}/…)이거나, ID 토큰의 picture 클레임과 같은 Google 아바타 URL이어야 합니다. 다른 사람의 사진이나 임의의 외부 URL은 쓸 수 없습니다.
  • 프로필은 get만 허용합니다. 목록 조회를 막아 사용자 목록을 통째로 가져갈 수 없게 합니다.

publicName이 유일하도록 publicNames/{key} 선점 문서를 씁니다.

  • 선점 문서는 생성만 가능하고 덮어쓸 수 없습니다. 먼저 만든 사람이 이름을 가집니다.
  • 선점은 "같은 배치가 끝난 뒤 내 프로필이 그 이름을 갖는 경우"에만 만들 수 있습니다(getAfter). 쓰지도 않는 이름을 미리 차지할 수 없습니다.
  • 이름을 바꿀 때 예전 이름의 선점은 같은 배치에서 지워야 합니다.
  • 선점 제도 이전 사용자의 이름은 배포 전후에 backfillPublicNames로 선점을 만들어 둡니다. → 배포

약관 동의 ​

users/{uid}.consent는 약관 동의와 만 14세 이상 확인 기록입니다. → 약관 동의와 연령 확인

text
users.consent: 정확히 { termsVersion: 1~32자 문자열, ageConfirmed: true, at: request.time }
               생성 때 또는 수정 때 통째로 씀 (새 버전 동의 = 다시 씀)
               지우거나 일부만 바꾸는 수정 → 거부
gratitudes, comments create: get(users/{auth.uid}).data.consent is map  (hasConsent)
  • 동의 화면은 클라이언트 화면이라 건너뛸 수 있으므로, 규칙이 UGC(글·댓글)를 만들 때 동의 기록을 직접 확인합니다.
  • 규칙은 기록이 있는지만 봅니다. 현재 버전인지는 클라이언트가 판단해 다시 묻습니다. 약관 버전을 올릴 때 규칙을 다시 배포하지 않아도 되게 하기 위해서입니다.
  • users 문서가 없으면 get()이 실패해 거부됩니다. 새 사용자의 첫 글은 로그인 동기화(users 생성)를 기다립니다.

삭제·정지 직후의 쓰기 차단 ​

Firebase Auth 사용자를 지우거나 정지해도, 이미 발급된 ID 토큰은 최대 1시간 동안 규칙과 callable을 통과합니다. 그래서 서버가 계정 삭제·이용 정지 직후에 서버 전용 문서 disabledUsers/{uid}(expireAt 2시간 뒤)를 쓰고, 규칙은 모든 생성 경로에서 이를 확인합니다.

text
isActiveUser() = !exists(disabledUsers/{auth.uid}) || get(…).data.expireAt < request.time
확인하는 곳
users 생성·수정, publicProfiles 생성·수정, publicShares 쓰기삭제한 계정이 문서를 되살리지 못하게
gratitudes, comments, reports, feedback, analyticsEvents 생성정지한 계정이 계속 쓰지 못하게
users/{uid}/blocks, pushTokens 생성·수정남은 데이터가 생기지 않게
  • 비용을 줄이려고 형태 검사 같은 싼 조건 뒤에 둡니다. 교차 읽기는 1번(있으면 같은 문서 get 포함 2번)입니다.
  • callable도 같은 문서를 확인합니다(requireActiveUser: createCircle, joinCircle, submitQuestion). → Cloud Functions
  • 읽기와 삭제(차단 해제, 토큰 삭제)는 막지 않습니다.

감사 글: get과 list 분리 ​

Firestore는 단건 읽기(get)와 쿼리(list)를 다르게 평가합니다.

getlist
평가 방식실제 문서(resource.data)로 판단쿼리가 돌려줄 수 있는 모든 문서가 규칙을 통과해야 함
허용 조건작성자이거나, 숨기지 않은 글이면 groupId의 현재 멤버, 또는 운영자(다른 사람이 볼 수 있는 글만)쿼리 조건이 작성자 또는 멤버 조건을 보장해야 함

허용되는 쿼리 형태:

쿼리쓰는 곳교차 읽기
where('userId', '==', 내 uid) [+ createdAt 범위·정렬, startAfter]홈 "내 기록" 탭(실시간 첫 20개 + 더 보기), MyPage, 캘린더0
where('groupId', '==', X) [+ createdAt 범위] + orderBy('createdAt') (X의 멤버)Circle 피드, 오늘의 활동1 (요청당 캐시)

필터 없는 조회, 다른 사람의 userId, 내가 속하지 않은 groupId, 그리고 groupId in [...]는 거부됩니다. in 쿼리를 막는 이유는 그룹마다 get()이 하나씩 필요해 교차 읽기 한도를 넘을 수 있기 때문입니다. 그래서 클라이언트는 그룹마다 쿼리를 따로 보냅니다(다중 그룹 통합 피드는 아직 없음).

작성자 조건을 먼저 검사하므로, 작성자는 Circle을 떠나거나 Circle이 삭제된 뒤에도, 글이 숨겨진 동안에도 자기 글을 읽을 수 있습니다. → 결정 기록 #2, #4

숨김(moderation.status == "hidden")은 get에서만 규칙으로 판단합니다. 쿼리는 숨김 여부를 조건으로 표현할 수 없기 때문입니다(필드가 없는 예전 문서가 부등호 필터에서 빠짐). 대신 숨긴 Circle 글은 서버가 groupId를 비워 Circle 피드 쿼리에서 빠지게 하고, 목록에 보일지는 클라이언트(canSeeItem)가 한 번 더 정합니다. → 자동 숨김

감사 글: 생성과 수정 ​

생성 — 단일 setDoc, 자동 ID, 정해진 11개 필드만. 기본은 개인 글(groupId: null)이고, Circle 공유는 작성자가 고른 경우에만 groupId가 들어갑니다(규칙은 둘 다 허용하고, 기본값은 클라이언트가 정함 → 공개 범위):

  • userId == auth.uid, groupId가 있으면 현재 멤버
  • title 0~100자, content 1~3000자 (바이트가 아니라 글자 수)
  • 작성자 필드 == 공개 프로필
  • reactions는 4개 이모지의 빈 배열, isPublic == false, createdAt == request.time
  • 약관 동의 기록이 있고(hasConsent), 계정이 잠겨 있지 않음(isActiveUser)
  • moderation 필드는 만들 수 없음(정해진 필드 목록에 없음)

수정 — 정확히 두 가지 형태만 허용합니다.

형태누가바뀌는 필드조건
리액션 토글글을 읽을 수 있는 사람reactions이모지는 ❤️ 🙏 ✨ 🔥 중 하나, 바뀐 것은 본인 uid의 추가·제거뿐, 배열 중복 없음
공개 전환작성자isPublic, sharedAtisPublic은 bool, sharedAt은 null 또는 이번 요청의 서버 시간. 숨긴 글은 공개로 바꿀 수 없음(비공개로는 가능)

리액션과 다른 필드를 함께 바꾸는 요청, commentCount·moderation 변경, 내용·작성자·그룹 변경은 모두 거부됩니다. 예전 문서의 다른 이모지 키는 그대로 둘 수 있지만 수정할 수는 없습니다. 운영자의 리액션·댓글 권한은 늘어나지 않습니다(운영자 읽기는 get에만 따로 붙임).

삭제 — 작성자만 지울 수 있습니다. 댓글 하위 컬렉션과 통계는 onGratitudeDeleted 트리거가 정리합니다(규칙은 하위 컬렉션을 지우지 않음). → 감사 글 삭제

댓글 ​

동작조건
get부모 글을 읽을 수 있는 사람 (숨긴 댓글은 그 작성자만), 또는 운영자 (다른 사람이 볼 수 있는 글의 댓글만)

댓글 생성은 규칙에서 교차 읽기를 5번(부모 글, 그 그룹, 공개 프로필, users, 잠금 문서) 하는, 가장 비싼 단일 요청입니다.

외부 공유 opt-in ​

공유 페이지는 Admin SDK를 쓰는 shareRenderer가 렌더링하므로, 공개 여부는 규칙이 아니라 서버 코드가 판단합니다. 규칙은 그 판단의 입력을 지킵니다.

  • 감사 글: isPublic·sharedAt은 작성자만 바꿀 수 있습니다.
  • 캘린더 월·배지: publicShares/{uid}는 본인만 읽고 씁니다. calendarMonths(최대 120), badgeIds(최대 200) 두 목록만 허용합니다.

로그인하지 않은 사람은 Firestore에서 글을 직접 읽을 수 없습니다. 공유 페이지의 내용은 서버가 HTML에 넣어 준 것만 보입니다. 숨긴 글은 공개 상태여도 서버가 "비공개"로 보여 줍니다. → 감사 글과 공유

신고·차단·숨김 ​

기능 설명은 신고·차단과 자동 숨김에 있습니다.

text
reports:            create → 로그인 사용자가 자기 이름으로, 자동 ID, 정해진 형태, 활성 계정
                    read   → 운영자만 (get, list) — 신고한 본인도 읽을 수 없음
                    update, delete → 거부 (상태 변경·익명화는 서버)
users/{uid}/blocks: read, delete → 본인
                    create, update → 본인, { createdAt: request.time }만, 자기 자신 차단 불가, 활성 계정
disabledUsers:      읽기·쓰기 모두 거부

신고 생성 형태(isValidNewReport):

  • 필드는 reporterId, targetType, targetId, parentId, reason, detail, status, createdAt만. reporterId == auth.uid, status == "open", createdAt == request.time
  • targetType은 5종, reason은 7종 중 하나. ID 값은 [A-Za-z0-9_-] 1~128자(운영자 화면이 이 값으로 문서 경로를 만들기 때문)
  • 댓글 신고는 parentId(부모 글)가 필수, 그 밖은 없거나 null. 자기 자신을 사용자로 신고할 수 없음
  • detail은 없음·null·500자 이하 문자열
  • 대상 문서를 규칙에서 읽지 않습니다. 교차 읽기를 줄이고, 더 이상 읽을 수 없게 된 대상(나간 Circle의 글 등)도 신고할 수 있게 하기 위해서입니다. 대상 정보는 onReportCreated가 채웁니다.
  • 규칙은 개수를 셀 수 없어 도배는 서버가 처리합니다(24시간에 20개 초과 → spam).

운영자 읽기는 다른 사람이 볼 수 있는 글로 한정합니다(hasAudience: groupId가 있거나, 숨겨져 moderation.groupId에 Circle이 있거나, isPublic). 신고된 콘텐츠를 판단하는 데 필요한 만큼만 열고, "나만 보기" 글과 그 댓글은 운영자도 읽을 수 없습니다. isAdmin() 확인은 항상 마지막에 둬서 일반 사용자의 읽기에는 교차 읽기가 늘지 않습니다.

질문 제안 ​

제안한 질문은 사전 검토를 거칩니다. 운영자가 선정하기 전에는 제안자 본인과 운영자만 읽을 수 있고, 선정된 질문만 다른 사용자에게 보입니다. 클라이언트 쓰기는 운영자를 포함해 모두 거부하고, 검증·한도·상태 변경은 callable이 합니다. → 질문 제안과 선정

text
questions:         read  → 로그인 사용자이고
                            status == 'approved'  (누구나: 질문으로 쓰기)
                            || authorId == auth.uid (제안자: 모든 상태)
                            || isAdmin()            (운영자: 검토 대기열)
                   write → 모두 거부 (운영자도 callable로만)
questionOriginals: read  → 운영자만 / write → 거부

허용되는 쿼리 형태:

쿼리쓰는 곳
where('status', '==', 'approved') [+ kind, limit]질문으로 쓰기 (누구나)
where('authorId', '==', 내 uid) + orderBy('createdAt', 'desc')MyPage 내가 제안한 질문
where('status', '==', X) [+ orderBy('createdAt')], 상태별 개수운영자 검토 화면
  • gratitudes와 달리 get과 list를 나누지 않습니다. 세 분기 모두 쿼리 조건(status ==, authorId ==)이나 요청자(isAdmin())만으로 판단할 수 있어 하나의 read 규칙으로 정확히 표현됩니다.
  • 다른 사람의 검토 중·반려·숨김 질문, 상태를 섞은 쿼리, 필터 없는 조회는 운영자가 아니면 거부됩니다. 로그인하지 않은 사람은 선정된 질문도 읽을 수 없습니다.
  • 운영자 확인(isAdmin())을 마지막에 두어, 선정된 질문과 본인 질문을 읽을 때는 교차 읽기가 생기지 않습니다.
  • 선정된 질문 문서는 필드 단위로 숨길 수 없습니다. 그래서 검토한 운영자의 uid는 adminAuditLogs에, 운영자가 고치기 전 제안 원문은 questionOriginals에 두고, 질문 문서에는 공개해도 되는 값만 둡니다. authorId는 uid이지만 공개 프로필과 함께 이미 공개되는 값입니다.

Storage 규칙 ​

경로읽기쓰기
profilePhotos/{uid}/{file}누구나본인, 이미지, 5MB 미만
circlePhotos/{groupId}/{file}누구나그 Circle의 관리자, 이미지, 5MB 미만
그 밖의 경로거부거부

클라이언트는 올리기 전에 사진을 긴 변 512px JPEG로 줄이고(src/lib/imageResize.js, 원본은 10MB까지 받음), Cache-Control: public, max-age=31536000, immutable을 붙여 올립니다. 경로에 시각이 들어가 파일이 바뀌지 않으므로 기기·브라우저가 1년 동안 다시 받지 않습니다(Storage 기본값은 private, max-age=0이라 볼 때마다 다시 확인했음).

circlePhotos는 서비스 간(cross-service) 규칙입니다. Storage 규칙이 firestore.get()으로 groups/{groupId}.adminId를 읽어 관리자인지 확인합니다. Circle 문서가 없으면 실패(거부)합니다.

첫 배포 시 권한 부여

cross-service 규칙이 동작하려면 Storage 규칙 서비스 에이전트가 Firestore를 읽을 권한이 있어야 합니다. firebase deploy --only storage가 처음에 권한 부여를 묻습니다. → 배포

교차 문서 읽기 예산 ​

Firestore 규칙은 요청 하나당 get()/exists()를 10번(배치·트랜잭션은 20번)까지 허용합니다. 같은 문서를 다시 읽는 것은 캐시되어 한 번으로 셉니다.

요청교차 읽기
내 글 목록 조회0
Circle 피드 조회1 (그룹)
글 생성 (Circle 글)4 (그룹 + 공개 프로필 + users의 동의 + 잠금 문서)
리액션 토글 (Circle 글)1 (그룹)
댓글 생성5 (부모 글 + 그룹 + 공개 프로필 + users + 잠금 문서) — 단일 요청 중 최대
댓글 get3 (부모 글 + 그룹 + isAdmin)
프로필 이름 변경3 (새 선점 + 옛 선점 + 잠금 문서)
이름 변경 배치 전체5 (users + publicProfiles + 선점 2개 + 잠금 문서)
신고 생성, 차단, feedback·analyticsEvents·푸시 토큰 생성1 (잠금 문서)

새 규칙을 추가할 때는 이 표를 갱신하고 한도 안에 있는지 확인하세요. 다중 그룹 쿼리(groupId in [...])를 허용하지 않는 것도 이 예산 때문입니다.

tests/rules/는 루트와 독립된 npm 패키지입니다. Firestore·Storage 에뮬레이터를 demo-grato 프로젝트로 띄우고 @firebase/rules-unit-testing으로 규칙을 검증합니다.

text
tests/rules/

cd tests/rules
npm test     # JDK 21 필요 (JAVA_HOME)
  • beforeEach마다 Firestore를 비우고 seed()로 같은 세계(사용자 alice·bob·carol·erin·root, Circle g1·g2, 예전 형식 문서 등)를 만듭니다.
