iOS·Android 앱 ​

상태: 진행 중 (3단계)

네이티브 프로젝트와 앱 전용 기능(네이티브 로그인, 푸시, 휴대폰 자체 매일 알림, 링크로 앱 열기, 화면 처리)의 코드가 들어갔습니다. 실제 기기 확인, 서버·Hosting 배포, 스토어 제출은 남아 있습니다. → 로드맵 3단계

iOS·Android 앱은 기존 React 앱(dist/)을 Capacitor 네이티브 셸에 담아 만듭니다. 코드 대부분을 웹과 함께 쓰고, 웹뷰에서 동작하지 않거나 네이티브가 더 나은 부분만 플러그인으로 바꿉니다. → 결정 기록 #8

웹사이트는 그대로입니다. 앱 전용 코드는 모두 isNative 분기 안에 있고 플러그인은 그 안에서 동적으로 불러오므로, grato.today의 번들과 동작은 바뀌지 않습니다. → 웹 코드와 앱 코드의 경계

웹 코드와 앱 코드의 경계 ​

원칙: 웹사이트는 앱 코드 때문에 한 바이트도 바뀌지 않는다.

  • src/lib/platform.js의 isNative는 @capacitor/core를 가져오지 않고, 앱이 문서 시작 전에 넣어 주는 window.Capacitor를 읽습니다. core를 가져오면 웹사이트의 첫 화면 코드에 들어가고 grato.today에도 window.Capacitor가 생기기 때문입니다.
  • 앱 전용 경로는 모두 if (isNative) 안에 있고, 플러그인과 src/lib/native/*는 그 안에서 import()로 불러옵니다. 웹 빌드에서는 따로 떨어진 코드 조각으로만 남고 받지 않습니다.
  • 앱에서는 main.jsx가 첫 렌더링 전에 <html>에 native, native-ios/native-android 클래스를 붙입니다. 앱 전용 CSS는 모두 html.native 아래에 있습니다.
  • App.jsx는 앱에서만 NativeBridge를 lazy로 붙입니다. 첫 화면을 그린 뒤 받으므로 시작을 막지 않습니다(ADR-13).
  • 기기 밖으로 나가는 링크(공유, 초대, 신고 메일)는 window.location.origin 대신 siteUrl()(https://grato.today)을 씁니다. 앱의 출처는 capacitor://localhost, https://localhost이기 때문입니다.

웹 빌드를 앱에 넣기 ​

처음 받았을 때와 웹 코드를 바꿀 때마다 실행합니다.

bash
npm run build     # dist/ (.env 필요)
npx cap sync      # dist를 두 네이티브 프로젝트로 복사, 플러그인·SPM 링크 갱신

앱은 실제 Firebase 프로젝트에 연결됩니다

npm run dev와 마찬가지로 .env의 프로젝트를 씁니다. 앱으로 테스트할 때는 테스트 계정을 쓰고, 다른 사람에게 보이는 Circle에 글을 올리지 않도록 주의합니다.

iOS ​

bash
npx cap open ios              # Xcode에서 App scheme → 시뮬레이터 또는 기기 선택 → Run
npx cap run ios --list        # 실행 대상 목록
npx cap run ios --target <ID> # Xcode 없이 빌드·실행
  • 서명은 자동(Automatic)이고 개발 팀이 프로젝트에 지정되어 있습니다. 실제 기기는 처음 한 번 설정 › 개인정보 보호 및 보안 › 개발자 모드를 켜야 합니다.
  • 푸시는 실제 기기에서 확인합니다. APNs 토큰을 받지 못하면 토큰 등록만 실패하고 앱은 정상 동작합니다(콘솔에 [push] 오류).
  • 웹 코드 디버깅: Mac Safari › 개발자용 › (시뮬레이터 또는 기기) › localhost.

Android ​

bash
npx cap open android          # Android Studio에서 Run
npx cap run android           # 또는 CLI로 빌드·설치·실행

# 명령줄 빌드 (JDK 21)
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
export PATH=$JAVA_HOME/bin:$PATH ANDROID_HOME=$HOME/Library/Android/sdk
cd android && ./gradlew assembleDebug   # app/build/outputs/apk/debug/app-debug.apk
  • 네이티브 Google 로그인은 빌드에 서명한 키의 SHA-1이 Firebase Android 앱에 등록되어 있어야 합니다. 개발 기기의 디버그 키는 등록되어 있습니다. 다른 컴퓨터에서 빌드하면 cd android && ./gradlew signingReport로 SHA-1·SHA-256을 확인해 Firebase 콘솔에 추가합니다.
  • google-services.json이 없으면 빌드가 실패합니다(푸시 없는 앱이 나가지 않도록 일부러 막음).
  • 에뮬레이터는 Google Play가 들어 있는 이미지를 씁니다(Google 로그인, FCM).
  • 웹 코드 디버깅: Chrome chrome://inspect.

로그인 ​

Google은 앱 안 웹뷰의 OAuth를 막고(disallowed_useragent), 팝업·리디렉트 흐름은 앱의 출처(capacitor://localhost)와 맞지 않습니다. 그래서 앱은 플랫폼의 로그인 화면으로 토큰만 받고, 세션은 웹과 같은 Firebase JS SDK가 만듭니다. → 결정 기록 #17

  • 로그인 화면과 버튼은 웹과 같습니다. authStore의 signInWithProvider가 앱에서는 src/lib/native/auth.js로 갈 뿐입니다.
  • capacitor.config.json의 FirebaseAuthentication.skipNativeAuth: true: 플러그인은 로그인 화면만 띄우고 토큰을 돌려줍니다. 세션은 JS SDK 하나에만 있습니다.
  • 플러그인은 패키지의 JS 진입점 대신 registerPlugin('FirebaseAuthentication')으로 등록합니다. 진입점이 함께 가져오는 웹 구현이 firebase/auth를 웹사이트의 시작 코드 조각에 끌어들이기 때문입니다.
  • 사용자가 로그인 창을 닫으면 오류 없이 그대로 둡니다. 그 밖의 네이티브 오류는 "로그인하지 못했어요. 잠시 후 다시 시도해주세요."로 바꾸고, 화면이 설명하는 Firebase 오류(auth/account-exists-with-different-credential 등)는 그대로 넘깁니다.
  • 이메일·비밀번호 로그인은 웹과 같습니다. 앱 내 브라우저 경고와 팝업 준비(prewarm)는 앱에서 건너뜁니다.

본인 확인과 계정 삭제 ​

  • 계정 삭제의 재인증도 같은 네이티브 시트 → reauthenticateWithCredential입니다. 시트를 닫으면 삭제 화면이 오류 없이 그대로 남습니다(isSignInCancelled).
  • Apple 연결 해제(App Store 5.1.1(v)): iOS는 네이티브 로그인이 주는 인증 코드(5분 유효)로, Android는 액세스 토큰으로 해제합니다. JS SDK의 revokeAccessToken은 액세스 토큰만 보내므로, iOS의 인증 코드는 Firebase iOS SDK와 같은 Identity Toolkit accounts:revokeToken 요청을 직접 보냅니다. → 계정 삭제

로그아웃 ​

  1. 아직 로그인된 동안 이 기기의 푸시 토큰 문서와 FCM 토큰을 지우고, 매일 알림을 취소하고 dailyReminderChannel을 되돌립니다(최대 3초, 느린 네트워크가 로그아웃을 막지 않음).
  2. JS SDK signOut.
  3. 네이티브 SDK도 로그아웃(기억된 Google 계정, Android Apple 로그인이 남긴 네이티브 세션. 최대 2초).
  4. 웹과 같이 기기 캐시를 지우고 /login으로 다시 불러옵니다.

다른 곳에서 세션이 끝난 경우(토큰 만료·취소)에도 1·3을 합니다.

앱도 웹과 같은 웹 API 키(.env)로 Firebase에 접속합니다. 이 키에 HTTP 리퍼러 제한을 걸면 앱의 요청(출처 capacitor://localhost, https://localhost)이 막힙니다. 키를 제한할 때는 앱용 키를 따로 두는 방식을 함께 정합니다. → 출시 준비 체크리스트

APNs 키 등록 (소유자 작업) ​

iOS 푸시는 Firebase가 Apple의 APNs로 보냅니다. 이 키가 없으면 iOS 앱에 푸시가 오지 않습니다(Android는 상관없음).

  1. Apple Developer › Certificates, Identifiers & Profiles › Keys에서 새 키를 만들고 **Apple Push Notifications service (APNs)**를 켭니다. .p8 파일은 한 번만 내려받을 수 있으니 저장소 밖 안전한 곳에 보관합니다. Key ID를 적어 둡니다.
  2. Firebase 콘솔 › 프로젝트 설정 › 클라우드 메시징 › Apple 앱 구성(iOS 앱 cc.mknw.grato) › APNs 인증 키 업로드: .p8 파일, Key ID, Team ID.
  3. 한 키로 개발·운영 APNs 환경을 모두 씁니다. 앱의 aps-environment는 개발 빌드에서 development이고, App Store·TestFlight용으로 서명하면 운영 환경이 됩니다.
  4. 확인: 실제 iPhone에서 앱 로그인 → 알림 허용 → pushTokens/{uid}/tokens에 platform: 'ios' 문서 → 다른 계정으로 같은 Circle에 글 → 알림이 오고, 누르면 그 글로 이동.

매일 알림 (휴대폰 자체 알림) ​

앱의 매일 알림은 서버 푸시가 아니라 휴대폰이 직접 띄우는 로컬 알림입니다. 고른 시각에 서버·네트워크 없이 옵니다. → 결정 기록 #16

  • 시각은 웹과 같은 notificationSettings.dailyReminderHour·dailyReminderMinute(KST, 15분 단위)입니다. 앞으로 14일 치를 하루씩 따로 예약합니다("매일 반복" 하나가 아니라서 오늘만 뺄 수 있음).
  • 오늘 이미 글을 썼거나 시각이 지났으면 오늘은 빼고 내일부터 예약합니다.
  • 다시 예약하는 때: 앱 시작·로그인, 앱으로 돌아올 때, 알림 설정을 바꿀 때, 글을 저장했을 때, 권한을 허용했을 때. 같은 계획이면 아무것도 하지 않습니다.
  • 알림 ID는 KST 날짜마다 하나(21000부터 64개를 돌려 씀)라, 다시 예약해도 이미 떠 있는 다른 날의 알림을 덮지 않습니다.
  • 기기가 KST라고 가정합니다. 다른 시간대의 기기에서도 KST 기준 같은 순간에 옵니다(웹 서버 알림과 같은 순간).
  • Android는 정확한 알람 권한(SCHEDULE_EXACT_ALARM)을 쓰지 않습니다(매니페스트에서 제거). 절전(Doze) 중에는 몇 분 늦을 수 있습니다. 시스템이 이미 정확한 알람을 허용한 기기에서만 정확한 알람을 씁니다.
  • 문구는 서버 알림과 같고, 누르면 /write로 갑니다.

서버 알림과 겹치지 않게. 이 기기에 알림을 예약하는 동안 users/{uid}.notificationSettings.dailyReminderChannel = 'local'과 dailyReminderLocalAt(서버 시각)을 씁니다. 서버 sendDailyReminder는 이 표시가 14일 안에 갱신된 사용자에게 푸시를 보내지 않습니다. 앱은 표시를 하루에 한 번까지만 갱신합니다.

상황결과
알림을 끄거나 권한이 없음이 기기의 예약 취소, 이 기기가 쓴 표시를 null로 → 서버 알림 대상으로 돌아감
로그아웃예약 취소, 표시 되돌림
앱 삭제·오래 열지 않음표시가 14일 뒤 만료되어 서버 알림이 다시 감 (그때는 예약해 둔 14일 치도 끝남)
웹과 앱을 함께 씀앱의 로컬 알림이 켜져 있으면 웹 브라우저에도 서버 매일 알림이 가지 않음 (한 사람에게 하루 한 번)

홈 화면 위젯 ​

iOS·Android 홈 화면 위젯이 연속일, 오늘 기록 여부, 이번 주 기록, 오늘의 질문을 보여 줍니다. iOS는 잠금 화면 위젯(원형: 연속일, 직사각형: 연속일·오늘 기록)도 있습니다. → 결정 기록 #18

크기내용누르면
작은 위젯🔥 N일 연속(또는 "감사 기록"), "오늘 기록 완료 ✓" / "오늘의 감사를 적어볼까요?"/write
중간 위젯위 내용 + 이번 주 일~토 점(기록한 날 채움, 오늘 테두리) + 오늘의 질문질문: 그 질문으로 "질문으로 쓰기", 나머지: /write
로그아웃 상태🙏 "로그인하고 감사 기록을 시작해요"/login

감사 글 내용은 위젯에 나오지 않습니다. 위젯은 휴대폰을 보는 누구에게나 보이므로 숫자·날짜·선정된(또는 기본) 질문만 씁니다.

데이터 흐름. 앱이 작은 요약본(snapshot)을 만들어 위젯이 읽는 곳에 저장하고 위젯을 다시 그리게 합니다. 위젯은 서버에 접속하지 않습니다.

  • 요약본(src/lib/native/widgetModel.js, v1): lastPostKey(마지막 기록 KST 날짜), streak(그날 기준 연속일), recentKeys(최근 14일 중 기록한 KST 날짜), questions(오늘부터 7일 치 날짜별 질문). 로그아웃이면 {v:1, signedIn:false}.
  • 오늘의 질문은 질문 목록(선정 질문, 없으면 기본 질문)을 날짜 순서로 돌립니다. 같은 날에는 누구나 같은 질문입니다.
  • 앱이 요약본을 쓰는 때(src/lib/native/widget.js, NativeBridge): 로그인·통계가 바뀔 때, 글을 저장한 직후, 앱으로 돌아올 때. 내용이 같으면 다시 쓰지 않습니다. 로그아웃할 때만(로그인 상태에서 로그아웃으로 바뀔 때) 로그아웃 상태로 바꿉니다. 앱이 잠금 중 백그라운드로 실행되어 저장된 세션을 아직 못 읽은 시작은 로그아웃으로 보지 않습니다(매일 알림 예약도 같음).
  • iOS는 앱이 열리고 닫힐 때마다(SceneDelegate) 위젯을 다시 그립니다. 요약본을 쓸 때 보낸 다시 그리기 요청이 앱 업데이트 직후처럼 무시되면 위젯이 옛 화면(예: 로그아웃 상태)에 머물렀기 때문입니다.
  • 위젯은 같은 규칙(widgetView)을 스스로 적용합니다. 그래서 앱을 열지 않아도 KST 자정에 "오늘 기록 여부"·연속일·이번 주·질문이 넘어갑니다. 규칙은 세 곳에 있으니 함께 고칩니다: JS widgetModel.js(기준, 테스트), Swift ios/App/GratoWidget/WidgetModel.swift, Java android/.../widget/WidgetModel.java(JUnit).
  • 질문 링크 https://grato.today/write?mode=guided&qtext=…&qid=…: WritePage가 질문 목록에서 id 또는 같은 문구의 질문을 찾을 때만 그 질문을 띄웁니다(목록에 없는 문구는 무시하고 평소처럼 고름).

네이티브 플러그인 GratoWidget (npm 패키지가 아니라 앱 프로젝트 안에 있음): setSnapshot({snapshot}), clear().

링크로 앱 열기 ​

초대·공유 링크(https://grato.today/invite/…, /share/…)를 앱이 설치되어 있으면 앱에서, 아니면 지금처럼 웹에서 엽니다.

플랫폼앱 쪽웹(Hosting) 쪽
iOS (Universal Links)App.entitlements의 applinks:grato.todaypublic/.well-known/apple-app-site-association: appIDs = <Team ID>.cc.mknw.grato, 경로 /invite/*, /share/*
Android (App Links)AndroidManifest.xml의 autoVerify intent filter: https://grato.today, /invite/, /share/public/.well-known/assetlinks.json: 패키지 cc.mknw.grato, 서명 인증서 SHA-256
  • firebase.json: AASA는 확장자가 없어 Content-Type: application/json 헤더를 붙이고, SPA 재작성에서 /.well-known/**을 빼고, appAssociation: "NONE"으로 Hosting이 자체 연결 파일을 만들지 않게 합니다. 두 파일은 Hosting을 배포해야 실제로 열립니다.
  • 앱은 appUrlOpen 이벤트와 처음 실행한 링크(getLaunchUrl)를 deepLinks.appPathFromUrl로 앱 경로로 바꿔 라우터로 이동합니다. 같은 링크가 두 번 오면(iOS 콜드 스타트) 3초 안의 두 번째는 무시합니다. https://grato.today가 아닌 주소는 무시하고, 앱에 없는 사이트 페이지는 첫 화면으로 갑니다.
  • 초대 링크의 로그인 전 흐름(pendingInviteCode)은 웹과 같습니다.
  • iOS는 앱을 설치할 때 Apple CDN을 거쳐 AASA를 받습니다. 파일을 바꾸면 반영까지 시간이 걸릴 수 있고, 확인할 때는 앱을 지웠다 다시 설치합니다.

확인 방법

bash
# iOS 시뮬레이터
xcrun simctl openurl booted https://grato.today/invite/ABC123
# Android
adb shell pm verify-app-links --re-verify cc.mknw.grato
adb shell pm get-app-links cc.mknw.grato          # grato.today: verified
adb shell am start -a android.intent.action.VIEW -d https://grato.today/invite/ABC123

출시 전에 출시용 SHA-256을 추가합니다

지금 assetlinks.json에는 개발용 디버그 키의 지문만 있습니다. Play 스토어 앱은 Google Play 앱 서명 키로 서명되므로, Play Console › 설정 › 앱 무결성 › 앱 서명에 나오는 SHA-256(직접 서명한 출시 빌드를 기기에서 시험한다면 업로드 키의 SHA-256도)을 sha256_cert_fingerprints 배열에 추가하고 Hosting을 배포합니다. 같은 지문(SHA-1·SHA-256)을 Firebase Android 앱에도 등록해야 Google 로그인이 됩니다.

화면 처리 ​

안전 영역 (safe area) ​

웹뷰는 화면 끝까지 그려집니다(viewport-fit=cover, Android 15 이상은 항상). 페이지가 상태 표시줄·노치·홈 인디케이터를 직접 피합니다. 모든 규칙은 src/index.css의 html.native 아래에 있어 웹사이트에는 적용되지 않습니다.

  • --safe-top, --safe-bottom: Android는 Capacitor SystemBars가 넣어 주는 --safe-area-inset-*(insetsHandling: "css"), iOS는 env(safe-area-inset-*).
  • #root에 위쪽 여백, 탭 막대가 없는 화면에만 아래쪽 여백(탭 막대는 이미 홈 인디케이터 위에 있음). .min-h-dvh 화면은 두 여백을 뺀 높이.
  • 고정 헤더(.top-bar)는 상태 표시줄 아래에 멈추고, 상태 표시줄 자리에는 띠(body::before, 헤더가 있으면 흰색, 아니면 페이지 색)를 깔아 스크롤한 내용이 비치지 않게 합니다.

상태 표시줄, 스플래시, 키보드 ​

  • 상태 표시줄: 밝은 배경에 어두운 글자(Style.Light). Android 14 이하는 웹뷰 위에 겹치지 않는 #FFF7ED 막대, Android 15 이상은 항상 화면 끝까지라 위의 안전 영역이 처리합니다. 내비게이션 막대 아이콘도 어둡게.
  • 스플래시: #FFF7ED, 300ms 뒤 자동으로 숨고 앱 셸이 시작되면 바로 숨깁니다.
  • 키보드: 웹뷰가 키보드 위로 줄어들고(resize: "native"), 입력 중인 칸을 보이게 스크롤하고, 그동안 아래 탭 막대를 숨깁니다(html.keyboard-open).
  • 다크 모드는 없습니다(웹 UI가 라이트만 있음). iOS UIUserInterfaceStyle = Light, Android 라이트 테마.

Android 뒤로 가기 ​

  1. 바텀 시트·대화상자가 열려 있으면 닫습니다(웹의 Escape와 같음).
  2. 첫 화면(/, /home, /login, /onboarding, /consent)이면 앱을 나갑니다.
  3. 그 밖에는 이전 화면으로, 이전 기록이 없으면 첫 화면으로 갑니다.

iPhone 뒤로 가기 (스와이프) ​

  • 화면 왼쪽 가장자리에서 오른쪽으로 밀면 이전 화면으로 갑니다. 웹뷰의 allowsBackForwardNavigationGestures를 ios/App/App/MainViewController.swift(CAPBridgeViewController 하위 클래스)에서 켭니다. 화면마다 React Router의 기록 항목이 있어 Safari의 뒤로 가기 스와이프와 같게 동작합니다.
  • 주의: Capacitor 8 템플릿의 SceneDelegate가 창을 직접 만들어 Main.storyboard의 화면을 버립니다. 그래서 SceneDelegate.swift에서도 MainViewController()를 써야 합니다(스와이프와 로컬 플러그인 등록이 여기에 달려 있음).
  • 로그인·동의 뒤 이동은 기록을 바꿔치기(replace)하므로 홈에서 밀어도 로그인 화면으로 돌아가지 않습니다.
  • 링크를 길게 눌렀을 때의 웹 미리보기는 끕니다(allowsLinkPreview = false).

앱 안의 링크 ​

  • https://grato.today/… 링크: 앱의 그 화면으로 바로 이동합니다.
  • 다른 사이트, 그리고 새 창으로 여는 앱 페이지 링크(가입 폼 옆 약관 등): 앱 안 브라우저(Safari View Controller / Custom Tabs)로 열어 지금 화면을 유지합니다.

아이콘과 브랜드 ​

브랜드 표시는 새싹 마크와 Grato 로고 글자입니다. 새싹은 한 줄기에서 돋은 작은 잎(#F59E0B)과 큰 잎(#FBBF24), 배경은 #FFF7ED입니다. 이모지(🙏)는 아이콘·로고에 쓰지 않습니다(애플 이모지 그림은 애플 저작물).

  • 마크: Gemini로 만든 시안(2026-10) 가운데 하나를 골라 벡터로 다시 그렸습니다(resources/brand-tools/trace.py → mark.json: 1000×847 상자의 두 경로, 절대 좌표 M/L/C/Z, even-odd). 모든 산출물이 이 파일 하나에서 나옵니다.

서버·Hosting 먼저 배포 ​

앱 빌드를 누구에게든(TestFlight, 내부 테스트 포함) 배포하기 전에 아래 서버 변경을 프로덕션에 올립니다. 순서는 배포와 같습니다(함수 → Hosting).

변경먼저 올리지 않으면
함수 utils/messaging.ts (앱 토큰에 notification 페이로드)앱 토큰에 데이터 전용 메시지가 가서 iOS·백그라운드 Android에 알림이 보이지 않음

보안 규칙과 인덱스는 바뀌지 않았습니다(notificationSettings의 새 키는 본인 쓰기 범위 안, pushTokens의 platform은 규칙이 확인하지 않음).

출시 서명 (Android) ​

  • 업로드 키: grato-upload (PKCS12, RSA 4096, 약 27년). 키 파일과 비밀번호는 저장소 밖(소유자 금고, 백업)에 둡니다. 잃어버리면 Play Console에서 업로드 키 재설정을 요청해야 하고 며칠 걸립니다.
  • android/keystore.properties(Git 제외)에 storeFile(절대 경로), storePassword, keyAlias, keyPassword를 적으면 app/build.gradle의 release 빌드가 이 키로 서명합니다. 파일이 없으면 release 빌드는 서명되지 않습니다.
  • Google Play는 앱 서명을 Google이 관리합니다(업로드 키로 서명한 AAB를 받아 Google의 앱 서명 키로 다시 서명). 그래서 Firebase·assetlinks.json에는 디버그 키, 업로드 키, (Play 등록 후) 앱 서명 키의 지문이 모두 들어갑니다.
  • 확인: keytool -printcert -jarfile app/build/outputs/bundle/release/app-release.aab의 SHA-256이 업로드 키와 같은지.
